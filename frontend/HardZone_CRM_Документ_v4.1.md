# HARDZONE CRM — Проектный документ

Версия 4.1 • Апрель 2026 • Пилот: HardZone, Хабаровск

---

## 1. Процесс разработки

1. Владелец продукта обсуждает сценарий и бизнес-логику.
2. Claude помогает сформулировать архитектуру и точное ТЗ.
3. ChatGPT реализует код, деплоит на сервер и проверяет результат.
4. Все изменения фиксируются в этом документе как в рабочей спецификации.

**Роли:**
- **Claude** — продуктовые решения, архитектура, формулировка ТЗ
- **ChatGPT** — код, деплой, миграции, проверка на сервере
- **Заказчик** — финальное решение по бизнес-логике и приоритетам

## 5. Роли и доступ

Сейчас в системе уже работает серверная авторизация сотрудников:
- вход по `email` и паролю;
- серверная сессия через `HttpOnly` cookie;
- frontend не хранит публичный токен и ходит в backend через server-side proxy;
- владелец управляет сотрудниками из скрытого раздела `/admin/users`.

Текущая модель доступа:
- `owner` — системная роль владельца;
- `admin` — рабочая роль сотрудника;
- реальные права задаются не жёсткими пресетами, а ручными доступами к модулям.

Настраиваемые доступы:
- склад;
- услуги;
- продажи;
- клиенты;
- расписание;
- аналитика;
- сотрудники и доступы.

Дополнительно:
- логин сотрудника = его `email`;
- новый пароль можно отправить сотруднику по email;
- восстановление доступа работает через почтовый сервис.

## 6. Модуль 1 — Склад

### 6.1 Концепция

В модуле `/warehouse` находятся только позиции с физическим остатком:
- товары;
- расходники.

Услуги полностью вынесены в отдельный модуль `/services`.

### 6.2 Типы позиций

| Тип | Продажа | Остаток | Закупка |
|-----|---------|---------|---------|
| Товар | Да | Да | Да |
| Расходник | Нет | Да | Да |
| Услуга | Нет в складе | Нет | Нет |

### 6.3 Правила склада

- при приёмке обновляются и `stock`, и `cost_price`;
- история склада показывает приёмки, списания и продажи;
- продажа через кассу списывает остаток только после подтверждения оплаты;
- в складской истории продажи подтягиваются из `orders`, а не из старой таблицы `sales`.

### 6.4 Ключевые сценарии

- создание и редактирование карточки товара;
- импорт из Excel;
- приёмка;
- ручное списание;
- инвентаризация;
- архивирование;
- просмотр единой истории движения.

## 7. Модуль 2 — Услуги

### 7.1 Концепция

В модуле `/services` находятся все продаваемые позиции без физического остатка:
- разовые посещения;
- абонементы;
- персональные и сплит-тренировки;
- прочие сервисные позиции клуба.

Услуги физически лежат в общей таблице `products`, но отделяются по `product_types.has_stock = false`.

### 7.2 Параметры услуги

Каждая услуга может иметь параметры абонемента:
- `subscription_type`: `single | visits | period | unlimited`
- `visits_total`
- `validity_days`
- `activation_type`: `purchase | first_visit`
- параметры заморозки
- `is_family`
- привязка к видам тренировок

### 7.3 Виды тренировок

В `training_types` хранится каталог видов тренировок:
- название;
- цвет;
- длительность;
- вместимость по умолчанию;
- описание;
- `slot_type`: `group | personal`.

Важно:
- в рабочем интерфейсе сейчас используются только **групповые** и **персональные** виды;
- `rental` из ранней схемы отложен и скрыт из UI.

### 7.4 Автоактивация услуги

После подтверждения оплаченного заказа:
- если в чеке есть услуга;
- и заказ привязан к клиенту;
- CRM автоматически создаёт `client_subscriptions` по параметрам услуги.

Ручная активация абонемента из карточки клиента убрана.
Если нужно выдать доступ вручную — это делается через продажу со скидкой `100%`.

## 8. Модуль 3 — Продажи

### 8.1 Концепция

CRM работает как **предкасса**:
1. администратор собирает чек в CRM;
2. заказ отправляется в aQsi как отложенный;
3. оплата проходит на кассе;
4. CRM получает подтверждение и только после этого:
   - списывает склад;
   - активирует услуги клиенту;
   - сохраняет фискальные данные.

### 8.2 Клиент в чеке

- если в чеке только товары — клиент необязателен;
- если в чеке есть услуга или абонемент — клиент обязателен;
- выбор клиента доступен по поиску и по штрихкоду;
- `client_id` сохраняется в `orders`.

### 8.3 Статусы заказа

| Статус | Значение |
|--------|----------|
| `open` | заказ открыт или отправлен на кассу |
| `confirmed` | оплачен |
| `cancelled` | отменён |
| `refunded` | оформлен возврат |

### 8.4 Скидки

Поддерживаются:
- скидка на весь чек;
- скидка на отдельную позицию;
- формат `%` или фиксированная сумма.

Скидки уходят и в CRM-расчёт, и в payload для aQsi.

### 8.5 Возвраты

Возврат сейчас:
- только финансовый;
- через aQsi;
- без движения по складу;
- по всему чеку целиком.

Для возврата сохраняются фискальные поля:
- ФД;
- ФН;
- ФП;
- РН ККТ;
- дата чека.

### 8.6 Интеграция с aQsi

| Параметр | Значение |
|----------|----------|
| Base URL | `https://api.aqsi.ru/pub` |
| Shop ID | `263355` |
| Warehouse ID | `ed3ea8c1-135c-431d-973b-d94092d5d478` |
| Устройство | `CS10F` |
| Налогообложение | УСН доход (`taxationSystem: 1`) |
| Авторизация | `x-client-key: Application {AQSI_API_KEY}` |

### 8.7 Подтверждение оплаты

Используются несколько уровней подтверждения:
- webhook от aQsi;
- ручная кнопка проверки оплаты в истории продаж;
- фоновая повторная синхронизация через backend.

Это сделано потому, что webhook от aQsi на практике может приходить нестабильно.

## 9. Модуль 4 — Клиенты

### 9.1 Карточка клиента

Основные поля:
- ФИО;
- телефон;
- email;
- дата рождения;
- персональная скидка;
- штрихкод;
- комментарий.

### 9.2 Интерфейс клиентов

Текущий основной сценарий:
- список клиентов `/clients`;
- раскрытие информации прямо в строке;
- отдельная кнопка-стрелка справа для перехода в полную карточку `/clients/:id`.

В раскрытом виде можно быстро увидеть:
- дату рождения;
- скидку;
- штрихкод;
- текущий абонемент;
- комментарий.

Поля `status` и `status_comment` остаются в БД и API, но скрыты в UI как малополезные для повседневной работы клуба.

### 9.3 Абонементы клиента

Абонементы:
- создаются автоматически после оплаты услуги;
- привязываются к клиенту и услуге;
- поддерживают остаток занятий, срок, семейный режим и статус.

Поддерживаемые статусы:
- `active`
- `frozen`
- `expired`
- `exhausted`

### 9.4 Заморозка

Реализованы:
- заморозка;
- разморозка;
- история заморозок;
- продление срока действия при разморозке.

### 9.5 Посещения

`client_visits` хранит два типа посещений:
- `group`
- `open_gym`

### 9.6 Импорт

Импорт клиентов из CSV уже реализован.
Перенесено: **280 клиентов**.

## 10. Модуль 5 — Расписание и зал

### 10.1 Расписание тренировок

В модуле `/schedule` реализованы:
- виды просмотра: день / неделя / месяц;
- ручное создание занятий;
- регулярные шаблоны;
- детали занятия;
- запись клиента;
- фиксация посещения;
- управление тренерами.

### 10.2 Типы слотов

В рабочем интерфейсе слоты делятся на:
- `group`
- `personal`

Логика:
- вид тренировки сам определяет, к какому типу относится;
- список видов тренировок фильтруется по выбранному типу слота;
- вместимость по умолчанию берётся из вида тренировки.

### 10.3 Тренеры

Есть отдельный контур управления тренерами:
- список;
- создание;
- редактирование;
- мягкое удаление (`is_active = false`);
- привязка к видам тренировок.

### 10.4 Запись и посещение

Запись на тренировку:
- создаёт `bookings`;
- не списывает абонемент в момент записи;
- списание происходит только при фактической отметке посещения.

Фиксация посещения:
- сейчас основная UI-логика — кнопка по строке клиента в деталях занятия;
- после окончания занятия все неотмеченные записи автоматически переводятся в `missed` фоновым job раз в час.

### 10.5 Свободное посещение зала

Добавлен отдельный контур для `open_gym`:
- вкладка `Зал` в модуле расписания;
- часы работы зала по дням недели;
- отметка входа по поиску клиента или по штрихкоду;
- список сегодняшних посещений зала;
- индикатор, открыт зал сейчас или нет.

Важно:
- сейчас реализуется только **вход**;
- выхода из зала пока нет;
- это в первую очередь контур статистики посещаемости;
- отдельное списание абонемента за open gym пока не добавлено.

## 14. Приоритеты и технический долг

| Задача | Приоритет | Комментарий |
|--------|-----------|-------------|
| HTTPS + `Secure` cookie | Критично | сейчас сервер работает по `http`, поэтому cookie пока без `Secure` |
| Усилить внутренний auth-proxy между frontend и backend | Высокий | публичный токен уже убран из браузера, но внутри server-side proxy всё ещё используется общий сервисный секрет |
| Держать канонической одну папку миграций | Высокий | рабочая директория миграций — только `backend/src/db/migrations` |
| Дожать надёжный callback оплаты aQsi | Средний | сейчас есть webhook + ручной sync + fallback |
| Возврат отдельных позиций | Средний | сейчас возврат только всего чека |
| Open Gym: списание абонемента | Средний | пока `open_gym` используется как контур учёта посещаемости |
| Open Gym: выход из зала | Средний | пока фиксируется только вход |
| Аналитика продаж, посещений и абонементов | Средний | данные уже копятся и их пора выводить в полезные отчёты |
| Декомпозиция `app/sales/page.tsx` | Низкий | файл всё ещё слишком большой |
| Декомпозиция `app/schedule/page.tsx` | Низкий | модуль расписания тоже вырос и просится на разбиение |
| История изменения цен | Низкий | лог `cost_price` и `sale_price` |
