# HardZone Access Model

Цель: зафиксировать роли, права и ограничения до расширения CRM в Telegram/MAX, тренерскую админку и клиентское приложение.

## Главный принцип

HardZone должен развиваться как единая платформа:

```text
PostgreSQL + Backend API
        |
        ├─ Web CRM для owner/admin
        ├─ Web CRM для дежурного сотрудника
        ├─ Telegram/MAX интерфейс для клиентов
        └─ Telegram интерфейс для тренеров/дежурных
```

Бизнес-правила живут в backend. Web CRM, Telegram и MAX только вызывают API. Нельзя делать отдельную логику списаний, оплат, долгов или расписания внутри ботов.

## Роли и идентичности

Важно: права доступа и карточка тренера - разные сущности.

`users` отвечает за вход в CRM/Telegram-админку и набор прав.
`trainers` отвечает за профиль в расписании: кто ведет тренировку, какие типы занятий ведет, как отображается в сетке.

Связь между ними опциональная: `trainers.user_id`. Она нужна, чтобы сотрудник-тренер мог быть выбран в расписании и в будущем видеть свои занятия в Telegram. Эта связь не выдает права сама по себе.

### Owner / Главный администратор

Это владелец системы.

Может:

- видеть и менять всё;
- управлять пользователями и доступами;
- видеть системную диагностику;
- контролировать backup/restore;
- управлять продажами, клиентами, складом, расписанием, аналитикой;
- выполнять опасные операции восстановления AQSI;
- менять правила и настройки системы.

Нельзя:

- удалять или понижать последнего active owner без отдельного защитного правила.

### Admin / Администратор

Операционный администратор клуба.

Может:

- вести клиентов;
- продавать абонементы, услуги и товары;
- работать с заказами и оплатами;
- записывать клиентов;
- отмечать посещения;
- управлять расписанием, если выдан модуль редактирования;
- смотреть аналитику, если выдан доступ;
- работать со складом, если выдан доступ.

Ограничения:

- не управляет owner;
- не отключает системную безопасность;
- не меняет backup/restore процедуру;
- не получает системные опасные действия без явного доступа.

### Staff / Дежурный тренер

Это сотрудник смены. По должности он может быть тренером, но по доступу временно закрывает функции администратора, когда администратора нет у ноутбука.

Базово может:

- видеть расписание;
- записывать клиентов на тренировки;
- отмечать посещения;
- выбирать, с какого абонемента списать занятие;
- фиксировать неоплаченное посещение;
- видеть клиентов в объёме, нужном для записи и оплаты;
- проводить продажи, если работает на смене;
- принимать оплату через существующий CRM/AQSI flow.

Базово не может:

- отменять тренировки как события расписания;
- менять недельную сетку расписания;
- управлять пользователями и доступами;
- видеть системную диагностику;
- менять backup/restore;
- менять AQSI-настройки;
- редактировать глобальные правила клуба.

### Trainer / Тренер без смены

Это более узкий доступ, если понадобится отделить обычного тренера от дежурного сотрудника.

Может:

- видеть свои тренировки;
- видеть список записанных клиентов;
- отмечать посещения;
- оставлять рабочий комментарий по занятию, если такая функция появится.

Не может:

- продавать;
- видеть кассу;
- записывать клиентов вне разрешённого сценария;
- менять расписание;
- видеть чужие управленческие данные.

На текущем этапе можно не заводить отдельную роль `trainer` в коде, а сначала реализовать preset `Дежурный тренер`.

### Client / Клиент

Клиент не должен входить в CRM.

Клиентская идентичность нужна для Telegram/MAX и будущего клиентского приложения:

- мой абонемент;
- мои записи;
- мои посещения;
- долг / неоплаченные посещения;
- уведомления;
- оплата или ссылка на оплату.

Клиент видит только себя и свои записи. Клиентский доступ проектируется отдельно от `users` CRM.

## Текущая кодовая база

Сейчас в коде фактически используются:

```text
role: owner | admin
module_grants
module_revokes
```

Модули:

```text
warehouse
services
sales
clients
schedule
schedule_edit_groups
schedule_edit_personal
schedule_cancel
schedule_clients
schedule_attendance
schedule_gym
analytics
users_manage
```

Это хорошая база. Следующий шаг - не плодить жёсткие должности, а добавить понятные access presets.

## Access Presets

### Owner

Роль: `owner`.

Модули:

```text
all modules
```

### Full Admin

Роль: `admin`.

Модули:

```text
warehouse
services
sales
clients
schedule
schedule_edit_groups
schedule_edit_personal
schedule_cancel
schedule_clients
schedule_attendance
schedule_gym
analytics
users_manage
```

Примечание: если нужно ограничить администратора, ограничения лучше делать через `module_revokes`.

### Duty Trainer / Дежурный тренер

Роль: `admin` на текущей схеме, но с ограниченным набором модулей и `role_title = 'Дежурный тренер'`.

Модули:

```text
sales
clients
schedule
schedule_clients
schedule_attendance
```

Опционально:

```text
services
warehouse
```

Запрещённые модули:

```text
users_manage
analytics
schedule_edit_groups
schedule_edit_personal
schedule_cancel
schedule_gym
```

### Trainer Basic

Будущий preset, если понадобится:

```text
schedule
schedule_attendance
```

Вопрос к будущему решению: разрешать ли `schedule_clients` обычному тренеру без смены.

## Бизнес-правила доступа

### Расписание

- Тренировки планируются заранее на неделю.
- Дежурный тренер не отменяет тренировки.
- Дежурный тренер записывает клиентов на тренировки.
- Дежурный тренер отмечает посещения.
- Редактирование сетки расписания - admin/owner или отдельный модуль `schedule_edit_*`.
- Отмена тренировки - только через `schedule_cancel`, не в базовом доступе дежурного тренера.

### Посещения и неоплата

- Клиент может быть записан и отмечен даже если оплата не закрыта.
- При записи/отметке сотрудник выбирает, с какого абонемента списать занятие.
- Если оплаты нет, посещение фиксируется как неоплаченное.
- Неоплаченное посещение должно быть видно в карточке клиента и операционных списках.
- Это не “ошибка”, а рабочее состояние: долг / ожидает оплаты.

### Продажи

- Дежурному тренеру нужен модуль продаж, потому что в отсутствие администратора он работает за администратора смены.
- Продажи должны идти через существующий CRM/AQSI flow.
- Нельзя создавать чеки вручную вне CRM, если заказ уже имеет AQSI traces.

### AQSI-зависания

Рабочее правило:

- сначала использовать существующие действия восстановления/синхронизации;
- если заказ невозможно восстановить, отменить заказ в CRM и пробить заново;
- не создавать ручной свежий чек вне CRM для заказа с AQSI operation traces.

### Продление абонемента

Официальной “заморозки” по правилам нет.

Нужна простая операция:

```text
Продлить абонемент
```

Поля:

- количество дней;
- причина;
- кто продлил;
- дата операции.

Правило:

- безлимит на месяц не продлевать;
- остальные абонементы можно продлить вручную по решению администратора/owner.

## Telegram / MAX Roadmap

### Сначала backend contract

Перед ботами нужны API-контракты:

```text
/api/staff/me
/api/staff/schedule/today
/api/staff/bookings
/api/staff/book-client
/api/staff/mark-attendance
/api/staff/client-search
/api/staff/sales

/api/client/me
/api/client/subscriptions
/api/client/bookings
/api/client/visits
/api/client/debt
```

### Trainer Telegram MVP

Первый внешний интерфейс лучше делать для дежурного тренера:

- сегодняшние тренировки;
- список клиентов на тренировке;
- поиск клиента;
- запись клиента;
- отметка посещения;
- выбор абонемента для списания;
- фиксация неоплаченного посещения;
- базовая продажа/оплата, если нужна на смене.

### Client Telegram/MAX MVP

После тренерского MVP:

- мой абонемент;
- расписание;
- запись;
- мои посещения;
- неоплаченные посещения / долг;
- уведомления;
- оплата или ссылка на оплату.

## Текущее состояние реализации

Реализовано:

1. В UI управления сотрудниками добавлены access presets:
   - Full Admin / `Администратор`;
   - Duty Trainer / `Дежурный тренер`.
2. Owner не создается как отдельный preset в форме сотрудников: это защищенная системная роль.
3. `Настройки -> Система` доступны только пользователям с `users_manage`.
4. Backend `/api/system/status` также закрыт через `users_manage`.
5. Добавлена опциональная связь `trainers.user_id` для привязки карточки тренера к пользователю.
6. При создании сотрудника можно явно создать карточку тренера; пресет `Дежурный тренер` включает этот чекбокс по умолчанию.

Следующий кодовый шаг:

1. Проверить backend guards для каждого модуля в критичных сценариях.
2. Убедиться, что staff без `schedule_cancel` не может отменить тренировку прямым запросом.
3. Доработать редактирование/привязку уже существующих карточек тренеров к сотрудникам.
4. После этого проектировать Telegram staff API.
