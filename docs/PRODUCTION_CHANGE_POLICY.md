# HardZone Production Change Policy

HardZone — действующая CRM. Администратор использует её как рабочую станцию, поэтому непрерывность работы и сохранность данных важнее архитектурной чистоты и скорости внедрения.

## Базовые гарантии

- Не менять текущий стек или схему деплоя без отдельного согласованного плана.
- Не переписывать целые рабочие модули ради рефакторинга.
- Не изменять существующие API-поля, статусы и семантику без проверки CRM, Telegram и MAX.
- Новые API-поля и коды ошибок сначала добавлять параллельно текущему формату.
- Не запускать автоматические тесты на production-базе или базе разработчика.
- Не использовать production для моков, demo-данных и экспериментальных сценариев.

## Классы изменений

### Без runtime-риска

Документация, unit-тесты, CI-проверки, защита тестовой БД и дополнительное логирование, если оно не меняет ответы API.

### Обратно совместимые

Добавление нового необязательного API-поля, нового endpoint или внутреннего сервиса при сохранении текущего поведения. Требуются тесты и staging-проверка затронутого сценария.

### Потенциально несовместимые

Миграции, изменение API-формата, авторизации, прав, AQSI, расписания, посещений или абонементов. Для них обязательны отдельная ветка, план отката, staging, свежий backup и restore-check перед production.

## Минимальный change gate

Перед правкой:

1. Описать текущий рабочий сценарий.
2. Определить затронутые endpoints, таблицы, роли и клиенты.
3. Зафиксировать текущее поведение тестом, если это возможно.
4. Определить staging- и production-проверку.
5. Для риска данных описать backup, restore-check и откат.

После правки:

1. Запустить минимальную релевантную проверку.
2. Для UI или runtime-изменений проверить staging.
3. Деплоить только через `deploy.ps1`.
4. Запустить production smoke-check и проверить затронутый сценарий.

## Правило API-совместимости

До отдельно согласованной миграции существующее поле `error` должно оставаться строкой. Машинные коды и идентификаторы запроса можно позже добавить только как новые поля:

```json
{
  "success": false,
  "error": "Абонемент закончился",
  "code": "SUBSCRIPTION_EXHAUSTED",
  "requestId": "req_123"
}
```

Текущие клиенты продолжат читать `error`, а новые смогут постепенно перейти на `code`.
