# Аудит раздела «Продажи» CRM HardZone

Дата актуализации: 13 июля 2026 года.

## Область аудита

Проверены:

- текущий экран продаж и история заказов;
- актуальный backend-контур `orders`;
- наличная и карточная оплата через AQSI V4;
- права сотрудников;
- позиции заказа, цены, скидки, склад и абонементы;
- возвраты и восстановление AQSI-операций;
- существующие backend-тесты.

Основные файлы:

- `backend/src/routes/orders.js`;
- `backend/src/routes/aqsi-v4.js`;
- `backend/src/services/aqsi-v4-flow.js`;
- `backend/src/services/aqsi.js`;
- `backend/src/services/order-sync.js`;
- `frontend/components/sales/`;
- `frontend/lib/api/orders.ts`.

## Подтверждённый кассовый процесс

1. Администратор формирует чек в CRM.
2. Для наличной оплаты CRM отправляет чек в AQSI через `send-to-aqsi`.
3. Для карточной оплаты CRM запускает операцию через `initiate-payment`, получает результат терминала и синхронизирует slip/чек.
4. CRM закрывает заказ после подтверждённого результата AQSI.
5. Если кассовая операция уже начата, администратор не отменяет её в CRM. Отмена выполняется непосредственно на кассе.
6. Результат отмены возвращается из AQSI в CRM, после чего CRM обновляет состояние текущего чека.

Отдельный пользовательский процесс «Черновик» не требуется. Добавлять кнопку отмены начатой AQSI-операции в CRM также не требуется.

## Реализованный пакет безопасности

В ветке `fix/sales-safety-hardening`:

1. Отключено прямое подтверждение заказа через `POST /api/orders/:id/confirm`. Актуальный frontend этот маршрут не использовал. Наличная и карточная оплата продолжают работать через штатные AQSI-маршруты.
2. Backend больше не доверяет присланным frontend значениям названия, SKU, цены, себестоимости и типа каталожной позиции. Эти данные берутся из CRM-каталога по `product_id`.
3. Произвольная позиция без существующего каталожного продукта не добавляется в заказ.
4. Количество должно быть положительным целым числом. Дробные и некорректные значения отклоняются.
5. Параметры истории `status`, `limit` и `offset` валидируются. Максимальный `limit` — 100.
6. Исправлены неверные названия маршрутов в диагностических сообщениях backend.
7. Добавлены регрессионные тесты прямого подтверждения и параметров истории.

Проверки пакета:

- frontend lint: без ошибок;
- backend syntax: пройден;
- удалённая изолированная PostgreSQL: 51 backend-тест из 51 пройден.

## Оставшиеся риски

### Высокий приоритет: идемпотентность возвратов

Сейчас запрос возврата в AQSI выполняется внутри открытой PostgreSQL-транзакции. Если AQSI успешно вернёт деньги, а локальный `COMMIT` затем завершится ошибкой, CRM может не сохранить `refunded_quantity` и допустить повторный возврат.

Рекомендуемое решение:

- отдельная таблица операций возврата;
- уникальный idempotency key;
- сохранение AQSI operation ID;
- состояния операции возврата;
- восстановление неопределённого результата без повторной отправки денег.

Пользовательский сценарий при этом не меняется: администратор выбирает позиции и подтверждает возврат. Меняется только внутренняя надёжность.

### Высокий приоритет: конкурентное изменение заказа

Часть операций проверяет открытый заказ до начала транзакции и без `FOR UPDATE`. Необходимо исключить изменение позиций одновременно с началом оплаты, не меняя интерфейс кассира.

### Средний приоритет: финансовый журнал

Нужна сохраняемая история событий:

- создание и изменение чека;
- применение скидки;
- запуск и результат оплаты;
- восстановление AQSI;
- частичный или полный возврат;
- сотрудник, время и причина действия.

### Средний приоритет: история продаж

Текущий UI показывает последние 50 записей. В дальнейшем нужны период, поиск, фильтры по сотруднику и способу оплаты, отдельный статус ручной сверки и пагинация.

### Средний приоритет: интерфейс возврата

Возврат использует системные `prompt` и `confirm`. Его следует заменить диалогом с позициями, количеством, суммой, скидкой и последствиями для товара или абонемента.

## Структура кода

`backend/src/routes/orders.js` остаётся большим файлом примерно на 1 500 строк. В рамках пакета безопасности он намеренно не рефакторился, чтобы не смешивать изменение поведения и перенос кода.

Безопасное последующее разделение:

```text
routes/orders.js
services/order-pricing.js
services/order-items.js
services/order-payment.js
services/order-refund.js
services/order-marking.js
repositories/orders.js
```

Переносить блоки следует по одному, начиная с чистых функций расчёта и маркировки. AQSI и возвраты переносить последними. После каждого шага запускать удалённые backend-тесты.

## Ограничения для следующих изменений

- Не добавлять отдельный процесс черновика без нового бизнес-требования.
- Не добавлять CRM-отмену уже начатой AQSI-операции.
- Не очищать AQSI traces при неопределённом результате.
- Не создавать свежий ручной чек для заказа с существующими AQSI operation traces.
- Не менять текущую последовательность оплаты без сверки со `swagger (3).json` и `docs/PAYMENTS.md`.
- Не совмещать большой рефакторинг `orders.js` с изменением кассовых бизнес-правил.
