# HardZone Agent Notes

- Зачёт `time_or_reps` объединяет завершивших (время ММ:СС, меньше лучше) и не завершивших (выполненные повторения, больше лучше). Все завершившие выше не завершивших, общий рейтинг мест с пропусками при равенстве. Хранить вид результата вместе со значением, не смешивать секунды с повторениями арифметически. Отдельно объяснять блокировку ввода отсутствием сетки и открытыми настройками оценки.

- Результаты соревнований: `docs/COMPETITION_RESULTS.md`. Баллы 100/95/90/85/80, затем минус 3, минимум 0; равные результаты делят место с пропуском следующих. Общий рейтинг сравнивает сумму, затем количества лучших мест. Финал скрывает ВСЕ публичные результаты с начала первого финального захода сохранённой сетки; hidden_at необратим обычными правками, кнопки публикации нет. Скрывать на backend, не только CSS. Не отдавать контакты/заявки через публичный рейтинг.
- Подтверждение комплекса заполняет следующие заходы по общему рейтингу, сохраняя время. Пересформирование сетки обязано учитывать результаты; нельзя удалить/перенести комплекс с результатами или менять состав категории с введёнными результатами. Пустой результат отличается от нуля.

- Кнопки добавления комплекса, перерыва и награждения имеют одинаковый нейтральный фон; бирюзовый фон появляется при наведении или клавиатурном фокусе. Не выделять добавление комплекса постоянной заливкой.

- Перерыв и общее награждение — `config.activities`, без категории. Предпросмотр смещений ничего не записывает; подтверждение показывает затронутые пункты и брифинги. Сдвиг идёт вперёд по площадке и категории, свободные интервалы поглощают задержку; удаление/сокращение не двигает остальные пункты назад. При сохранении проверять revision/source_hash. Обычное редактирование комплексов и количества обязано сохранять activities; сохранённая сетка обновляется отдельно.

- Категория комплекса выбирается в самой форме (при создании обязательный явный выбор). Редактирование может перенести тот же id в конец плана другой категории, сохраняя параметры; количество команд берётся из новой категории. Свёрнутые настройки показывают отдельные количества для всех категорий и не задают категорию нового комплекса.

- Отсутствие брифинга задаётся выключенным «Проводить брифинг» и `briefing_time: null`. `00:00` — реальное время, а не отсутствие; при включённом брифинге время обязательно. Нативное поле времени без явного выключателя вводило пользователя в заблуждение и приводило к брифингу с полуночи.

- Длинные названия команд показывать полностью с переносом внутри ячейки и автоматической высотой ряда. Минимальная целевая ширина дорожки 180 px, ограниченная шириной контейнера; длинное слово без пробелов не должно вызывать горизонтальное переполнение.

- В расчёте и сохранённой сетке дорожки делят доступную ширину поровну, названия команд центрируются. При нехватке ширины дорожки переносятся внутри захода на следующие ряды одинаковых ячеек, без горизонтальной прокрутки; колонки совпадают между заходами, включая неполный. Настройки категории и общего количества команд по умолчанию свёрнуты в «Настройки категорий».

- Редактирование существующего комплекса раскрывается внутри его карточки в расчёте, с сохранением и отменой там же, без перехода к отдельной форме наверху. Отдельная форма используется только для создания нового комплекса.

- В соревнованиях создание комплекса открывает отдельную форму; редактирование и удаление доступны на карточке в расчёте. Изменения комплекса сохраняются отдельным действием, удаление сразу сохраняет план. Плановое количество — общая настройка категории, не поле комплекса; сохранённая сетка остаётся отдельным снимком.

- Расчёт мероприятия должен показывать сами заходы со временем и дорожками до формирования сохранённой сетки: скрытие заходов оставляет один брифинг и создаёт впечатление, что комплекс не рассчитан.

- Вкладки мероприятия сохраняются в URL (`section`, `scheduleView`), чтобы обновление страницы возвращало в выбранный раздел; карточка мероприятия монтируется на клиенте после чтения `event` из URL.

- Мероприятия соревнований хранятся в `competition_events`; `event_key` изолирует категории, заявки и настройки. Личная ссылка оплаты определяется уникальным `public_token`, а настройки письма/оплаты — мероприятием этой заявки. Не возвращать фильтрацию автоматизации только по `COMPETITION_EVENT_KEY`. Действующая `/competition` остаётся ссылкой старого события; новые используют `?event=...`. Поддерживается существующий формат команд М + Ж.
- Настройки комплексов и сохранённая сетка разделены в `competition_schedules`: новые оплаты и редактирование плана только помечают сетку устаревшей. Пересформирование — отдельное действие с проверкой revision/source_hash. Первый комплекс каждой категории заполняется активными оплаченными заявками в порядке created_at DESC, id DESC; неполный заход идёт первым. Последующие комплексы до реализации результатов содержат только резерв мест. Учитывать общую площадку, брифинг и перерыв после комплекса при проверке пересечений.

- Акцент публичных соревнований и писем — `#c4c33a` — приглушённая версия жёлтого афиши CHALLENGE; бирюзовый CRM не должен наследоваться страницами соревнований. На статусе заявки не использовать декоративный квадрат с троеточием.

- В CRM соревнований статус участия выводится из отмены и подтверждённой оплаты: `registered` сам по себе не означает подтверждённое участие. Email показывать отдельной колонкой, включая «Не указан» для исторических заявок; отмена/восстановление не являются ручным подтверждением оплаты.

## Короткие правила

- Проект использует русскоязычный интерфейс; файлы с кириллицей сохранять в UTF-8.
- Для ручных правок использовать `apply_patch`, не PowerShell redirection и не `Set-Content` без явного контроля кодировки.
- Файл `текст` в корне проекта - пользовательский буфер для голосовых сообщений. Он может существовать пустым или временно меняться во время сессии; не читать, не редактировать, не удалять и не коммитить его.
- Коммитить в ветках по смыслу задачи, а не в случайно активной ветке; перед коммитом сверять текущую задачу с названием ветки.
- После frontend/backend-правок проверять mojibake или запускать `.\scripts\smoke-local.ps1 -SkipFrontendLint -SkipFrontendBuild -SkipBackendMigrate`.
- Backend/integration-проверки HardZone выполнять удалённо на сервере `79.137.162.55` или в CI. Не завязывать тестовый процесс на локальный компьютер, локальный Docker или локальный PostgreSQL.
- Для UI/продуктовых изменений HardZone не предлагать пользователю локальный `localhost` как место просмотра, если он явно этого не попросил. Основной контур просмотра - домен `https://hardzone.space` после деплоя через `.\deploy.ps1`.
- Не делать demo/mock/preview-роуты для продуктовых сценариев без явной просьбы. Сначала менять реальную CRM, затем Telegram/MAX как отображение тех же backend-данных.
- CRM является источником правды для клиентских, тренерских и дневниковых данных. Telegram Mini App только показывает и отправляет действия в backend; не проектировать отдельную логику или отдельные мок-данные внутри Mini App.
- Исполнитель может предлагать альтернативные решения и улучшения, но не может переделывать уже согласованные и готовые UX/бизнес-процессы без явного подтверждения пользователя.
- Новую бизнес-логику, дополнительные поля и комбинирование сценариев сначала обсуждать с владельцем продукта; не внедрять их как подразумеваемое расширение согласованной задачи.
- Production-сервер: `79.137.162.55`.
- Домен в настройке: `hardzone.space`, `www.hardzone.space`.
- Деплой с Windows запускать через `.\deploy.ps1`, подробности в `docs/OPERATIONS.md`.
- На ширине до 960px AppShell должен оставаться двухколоночным с компактным sidebar 64px: перевод `.app-grid` в одну колонку помещает `h-dvh` sidebar над workspace и полностью скрывает CRM-контент.
- Если frontend-деплой прерван по клиентскому таймауту во время `next build`, не перезапускать PM2 до появления полного `.next` с `prerender-manifest.json`; завершить сборку от пользователя `app`, затем перезапустить frontend.
- Перед risky production work запускать `.\scripts\backup-production.ps1` и проверять restore через `.\scripts\test-restore-production-backup.ps1`.
- Перед изменением AQSI сверять `swagger (3).json` и `docs/PAYMENTS.md`.

- На staging с production-копией данных не запускать фоновую синхронизацию AQSI без полного набора AQSI_BASE_URL, AQSI_API_KEY, AQSI_SHOP_ID: реальные заказы из копии иначе попадают в цикл ошибочных запросов.
- Зарплатные расчёты являются сохраняемыми ведомостями: изменение правил не пересчитывает прошлые ведомости; расход возникает только после отдельной отметки выплаты сотруднику.
- Чистый результат в финансах считается как выручка минус приёмки склада, внешние расходы и выплаченные зарплаты; складские списания показываются как потери, но повторно из результата не вычитаются, потому что деньги уже учтены при приёмке товара.
- В Telegram Mini App системные панели телефона из `.pen` служат только презентационной рамкой: не рендерить часы/сеть/батарею и не ограничивать рабочий контейнер `max-width: 390px`; интерфейс должен занимать всю область WebView Telegram.

## ОБЯЗАТЕЛЬНАЯ ПРИЁМКА UI-МАКЕТОВ

- ОБЯЗАТЕЛЬНО повторно открывать итоговый `.pen` с диска и проверять его после последних изменений при масштабе около 100%.
- ОБЯЗАТЕЛЬНО отдельно проверять текст, иконки, плашки, кнопки, повторяющиеся карточки и нижнюю навигацию: центровку, единую ось, отступы, переполнение, обрезание и наложения.
- НЕЛЬЗЯ считать работу завершённой, если нарушено хотя бы одно правило из `UI_DESIGN_PLAYBOOK.md`, выбранного UI-скилла, `AGENTS.md` или утверждённого пользователем решения.
- НЕЛЬЗЯ сообщать «готово» до повторной визуальной проверки уже сохранённого итогового файла. Проверка общего вида в уменьшенном масштабе не считается приёмкой.
- Повторяющиеся элементы ОБЯЗАТЕЛЬНО строить на общей сетке или компонентной геометрии; запрещено независимо подбирать координаты одинаковых элементов на глаз.
- Аналитика посещений не должна доверять `client_visits.visit_type = group` для занятий по расписанию: персональные и групповые посещения разделяются по `schedule_slots.slot_type`, а период — по локальной дате `APP_TIMEZONE`.
- Исторические активные клиенты в аналитике не считаются по текущему `client_subscriptions.status`: состояние на конец периода восстанавливается по датам действия, остатку с учётом последующих посещений и заморозкам.
- Клиентский Telegram Mini App не должен считать прошедшие сегодня занятия будущими: ближайшие записи и слоты фильтровать по полной паре date + start_time в APP_TIMEZONE, а не только по дате.
- Изолированный test-client frontend на общем домене обязан собираться с TELEGRAM_TEST_ASSET_PREFIX=/telegram-test-assets: без отдельного assetPrefix свежий HTML запрашивает /_next/... у основного frontend и Telegram WebView получает 404/MIME-ошибки.
- Контейнер Screen в клиентском Mini App должен оставаться flex-колонкой: без flex flex-col дочерний flex-1 overflow-y-auto не получает ограниченную высоту, из-за чего нижние части расписания и детальных карточек становятся недоступны.

- Статус «Вы записаны» в клиентском Telegram Mini App показывать только по подтверждённой будущей записи или available_slots.is_booked; свободный ближайший слот не является записью клиента.
- Карточки и подписи, визуально обещающие действие («Открыть пропуск», «Смотреть всё», реферальный баннер), должны быть настоящими кнопками с проверенным переходом; в Telegram WebView размер подписей нижней навигации фиксировать отдельным CSS-классом и проверять по computed style.
- Клиентский Telegram-кабинет нельзя привязывать по номеру, введённому вручную: разрешён только контакт `request_contact` с совпадающим `contact.user_id`; существующий `clients.telegram_id` не перезаписывать автоматически.
- Статус из публичного AQSI webhook не является доказательством оплаты: webhook только запускает серверную сверку, а заказ закрывается исключительно по подтверждённому ответу AQSI.
- Создание, изменение, заморозка и разморозка абонементов требуют `clients_update`; базовое право `clients` остаётся доступом только на чтение.
- Backend-тесты запускать только по `backend/test/*.test.js`: общий `node --test` ошибочно подхватывает production-файл `src/test-client-miniapp-server.js` и пытается занять порт 3002.
- Telegram poller должен повторять начальную настройку `deleteWebhook`/menu при сетевой ошибке: bootstrap вне retry-цикла превращает временную недоступность Telegram API в PM2 crash-loop после рестарта.
- При недоступности Telegram API с production VPS использовать только изолированный relay с `TELEGRAM_API_BASE` и секретным заголовком; не направлять через прокси CRM/AQSI и не возвращать ручную привязку клиента по номеру.
- Изолированный прогон deployed backend выявляет отдельную регрессию отмены записи: после `/api/staff/bookings/:id/cancel` `schedule_slots.booked_count` может остаться `1`; это не связано с Telegram relay и требует отдельного исправления.
- После изменения `TELEGRAM_API_BASE` или `TELEGRAM_RELAY_SECRET` перезапускать с обновлённым окружением все Telegram poller-процессы, включая `hardzone-test-client-bot`: старый тестовый процесс продолжает использовать прямой Telegram API и внешне остаётся `online`, одновременно выдавая постоянные `poll_failed: fetch failed`.
- Рабочий терминал соревнований Т-Банка одновременно обслуживает платежи конструктора: webhook HardZone обязан отвечать `OK` на валидные неизвестные `OrderId`, но менять заявку только после самостоятельного `/v2/GetState` и совпадения `PaymentId`, `OrderId` и суммы.
- `securepay.tinkoff.ru` использует цепочку НУЦ Минцифры, которую Node.js не доверяет по умолчанию: backend PM2 должен запускаться с `NODE_EXTRA_CA_CERTS=/srv/HardZone/backend/certs/russian_trusted_root_ca.pem`; запрещено обходить ошибку через отключение TLS-проверки.
- Повторная отправка полностью совпадающей заявки на соревнование должна продолжать оплату существующей записи, включая legacy-заявки без `public_token`; конфликтовать с `409` должна только попытка использовать участника в другой команде.
- Новый публичный frontend-маршрут нельзя считать доступным пользователю до production-деплоя и отдельной проверки без cookies: старая сборка может перенаправлять неизвестный путь на `/login`, даже если локальный proxy уже добавляет его в публичные исключения.
- На production Nginx направляет весь `/api/*` прямо в backend, поэтому публичная frontend-страница должна обращаться к реальному backend-маршруту; Next.js route handler под `/api/*` локально работает, но через домен будет обойдён.
- Автоматизация соревнований применяется только к новым заявкам с `payment_deadline`; исторические заявки не переводить на таймер задним числом. Для новых платежей передавать `RedirectDueDate`, а отменять заявку только после конечных неоплаченных статусов всех попыток: `Cancel` может вернуть уже списанные деньги при гонке оплаты. Неопределённый SMTP-ответ не означает неотправленное письмо — состояние `uncertain`/`sending` требует проверки перед повторной отправкой.
